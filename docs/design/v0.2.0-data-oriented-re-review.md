# Clean-Architecture Re-Review — Data-Oriented Lens on `typed/`

**Scope**: answer the question "is the `typed/` sub-package recommendation **data-oriented** for our codebase?"
**Method**: per-file runtime data-shape audit; hot path vs cold path analysis; "data outlives layers" mantra from the skill.
**Date**: this session.

> **Mantra:**
> 1. **The dependency rule is the only rule.** Source code dependencies point inward, always. Everything else is a heuristic.
> 2. **Data outlives layers.** Model the data and its transformations first; hang the layers off that, not the other way around.
> 3. **Every boundary has a price.** An abstraction earns its place by isolating volatile decisions or hot-path data shape — not by convention.
> 4. **Follow the data across the boundary.** At every crossing, ask: what shape enters, what shape leaves, what got copied, what got allocated.
> 5. **Purity is not the deliverable. A working, changeable, fast-enough system is.**

## 1. The data shapes in semanticdf

A data-shape trace from input to output:

```
YAML manifest string
  → SemanticManifest case classes      [shape: case-class record]
  → SemanticTable(op tree, metadata)   [shape: class wrapping an op ADT]
  → SemanticOp ADT (16 case classes)   [shape: immutable sealed ADT]
  → DataFrame (Spark columnar)         [shape: Column[] under the hood]
  → typed `T` (Row → case class)      [shape: case-class array — ONLY THIS is a data-shape-changing boundary]
```

**There is exactly ONE data-shape change in this system**: `DataFrame → T` via `ResultDecoder.decode(Row): T`. Everything else is **data shape-preserving**.

## 2. Hot path vs cold path

Per the data-engineering checklist:
> "Distinguish hot path (the recurring, scheduled, high-volume transform that runs every run) from cold path (one-off backfills, admin scripts) — indirection cost matters on the former, matters much less on the latter."

| Concern | Path | Per-row cost matters? |
|---|---|---|
| `SemanticField` (typed refs) | **Cold** — invoked at construction time (`.withMeasures[F]`) | No |
| `CalcExpr` (calc expression DSL) | **Cold** — invoked at construction time | No |
| `TypedArithmetic` (`Column + Column`) | **Cold** — invoked at construction time | No |
| `TypedMeasure` (`FieldRef[Carrier]`) | **Cold** — invoked at construction time | No |
| `CalcHelpers` (calc helpers) | **Cold** | No |
| **`ResultDecoder` (typed result collection)** | **Hot** at `collectAs[T]` / `queryAs[T]` — invoked once per terminal call (one shot — not per row during streaming) | Mild (one allocation per result set) |
| `ResultDecoderMacros` (derive) | **Compile-time** | No |

**Of the 7 files in the original `typed/` recommendation**:
- 6 are **cold path** / **compile-time** abstractions — data shape unchanged
- 1 is **hot path** at the `Row → T` boundary — `ResultDecoder`

## 4. The corrected recommendation

The previous JVM-Scala-lens recommendation was **NOT data-oriented**. It was typeclass-seam-oriented. Here's the data-oriented read:

### What the data lens ACTUALLY rewards

A sub-package for **`result/`**, holding 2 files:

```
io/semanticdf/result/
├── ResultDecoder.scala          (85 lines — typeclass + primitives)
└── ResultDecoderMacros.scala    (157 lines — derive macro)
```

**Why this earns its keep per the data-oriented lens**:

1. **The volatile decision isolated**: "how does a Spark DataFrame row decode to a typed case class?" — manual decode (ResultDecoder) vs Spark's native `Encoder[T]`. Two real options exist, both used in this codebase (ResultDecoder primitives + Spark's `.as[T]` in `queryAs`). Real boundary.

2. **The data-shape change**: `Row → T`. This is the **only** boundary in our typed surface where the data shape changes. The other 5 files (SemanticField, CalcExpr, etc.) don't change data shape — they're compile-time abstractions.

3. **The hot path**: mild. One allocation per terminal call (when the user collects or queries for a typed result). Not per row.

4. **The package name reflects the data**: `result/` — the typed-result concern. Same naming convention as `audit/` (the event log concern) and `cache/` (the cached result concern). All three are result-shaped sub-packages.

### What the data lens does NOT reward

A `typed/` sub-package holding 6 compile-time files (`SemanticField`, `CalcExpr`, etc.) is **NOT data-oriented**. Those 6 files:

- Don't change data shape at runtime
- Aren't on the hot path (they're invoked at construction time)
- Are compile-time type abstractions

The JVM-Scala reference says they form a "typeclass seam," but the **data-oriented lens** doesn't reward a sub-package for compile-time type abstractions — the boundary exists at compile time, not at runtime.

## 5. The honest answer to "is this data-oriented for our code base?"

**No, the JVM-Scala-lens recommendation (`typed/` for 7 files) was NOT data-oriented.** It was:
- ✅ Good per the JVM-Scala lens (typeclass seam placement)
- ❌ Over-broad per the data-oriented lens

The **data-oriented recommendation** is narrower and more focused:

| Lens | Recommendation | Files moved | Earns its keep? |
|---|---|---|---|
| JVM-Scala (JIT) | `typed/` for 7 files (SemanticField, CalcExpr, CalcHelpers, TypedArithmetic, TypedMeasure, ResultDecoder, ResultDecoderMacros) | ~510 lines | ✅ per JVM-Scala (typeclass seam) |
| **Data-oriented (this review)** | **`result/` for 2 files** (ResultDecoder, ResultDecoderMacros) | ~242 lines | ✅ per both lenses |

## 6. What this means in practice

The user asked: "is this data-oriented for our code base?"

**Answer**: The data-oriented read narrows the recommendation to **one sub-package: `result/`, holding 2 files**. This is:

1. **Half as much code movement** as the JVM-Scala-lens recommendation
2. **Half the blast radius** (2 files instead of 7; ~242 lines instead of ~510)
3. **A real data-shape boundary** (the `Row → T` boundary in `collectAs`/`queryAs`)
4. **Matches our existing sub-package naming convention** (`audit/` for the audit log, `cache/` for the cached result, `result/` for the typed result)

The other 5 files (`SemanticField`, `CalcExpr`, `CalcHelpers`, `TypedArithmetic`, `TypedMeasure`) are **compile-time type abstractions**. They don't change data shape and aren't on the hot path. They stay at the top level — the existing flat organization is fine for compile-time abstractions.

## 7. Disclosure / honesty

- **My earlier JVM-Scala-lens recommendation was correct under that lens** but failed to apply the data-oriented lens that the base skill explicitly requires. The skill says "Data outlives layers" — and our data shapes only change at one boundary.
- **The 5 compile-time files** are a real concern for JVM-Scala-lens discoverability, but the data-oriented lens doesn't reward a sub-package for them. **Different lenses, different recommendations.**
- **A 2-file sub-package `result/` is small**. But it's the smallest change that resolves the data-shape-boundary finding. Per the refactor mantra: "Make the smallest change that resolves that one finding."

## 8. Final recommendation

**Create `io/semanticdf/result/`**, move 2 files into it:
- `ResultDecoder.scala`
- `ResultDecoderMacros.scala`

**Severity (data-oriented lens)**: **HIGH** — this is the only typed-data-shape boundary in the library, and the typeclass lives alongside 28 unrelated files.

**Severity (JVM-Scala lens)**: **HIGH** for `ResultDecoder`. **LOW** for the 5 compile-time files — they're misplaced per JVM-Scala but not per the data-oriented lens.

**Risk**: low. The typeclass is referenced via implicit resolution (`decoder.decode(row)`) — moving the file changes 0 implicit search paths. Updating the import statements in the 2-3 call sites is mechanical.

If the user wants a broader JVM-Scala-lens organization (the `typed/` recommendation), that's a separate developer-experience decision, not a clean-architecture one. The data-oriented lens says: just move the 2 result files. The JVM-Scala lens says: move all 7 typed-surface files. Either is defensible; I'd recommend the data-oriented one.
