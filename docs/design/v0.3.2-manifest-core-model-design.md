# Design: Manifest → `core.Model` migration

**Status:** v1 — analytical. No code changes. The design doc is the deliverable.

**Version assumption: v0.3.2.** This is post-v0.3.1 work (v0.3.1 is functionally closed; release pending per user instruction). If this should be a different version (v0.3.2, v0.5.0, etc.), rename this doc + reference PRs accordingly.

**The TL;DR:** The current manifest layer (YAML → `SemanticTable`) is Spark-coupled; the engine-portable `core.Model` already exists as the target. A `ModelBridge.toModel` partial conversion already exists (PR history). What's missing is a **portable manifest reader** that produces `core.Model` directly from YAML (bypassing `SemanticTable`), plus a **dual reader** that supports both legacy and portable YAML side-by-side. The conversion is ~1,200-1,500 LoC across 2-3 PRs.

---

## 1. Current state

### Manifest formats in production

| Layer | Format | Reader | Output |
|---|---|---|---|
| **User-facing** | YAML | `YamlLoader` + `SemanticManifest` | `SemanticTable` (legacy, Spark-coupled) |
| **dbt bridge** | dbt `manifest.json` | `DbtManifestReader` | `SemanticTable` (via `DbtAdapter`) |
| **Ossie bridge** | Ossie project | `OssieReader` + `OssieProject` | `SemanticTable` (via `OssieAdapter`) |
| **SDF bridge** | SDF project | `SDFAdapter` + `SDFProject` | `SemanticTable` |
| **Engine-portable (target)** | (not yet) | (not yet) | `core.Model` |

### `SemanticTable` (the legacy shape)

Defined in `semanticdf-spark/src/main/scala/io/semanticdf/SemanticTable.scala`. Fields per the YAML loader:

- `name`, `description`, `version`, `status`
- `dimensions: List[Dimension]` — each with `SemanticScope => Column` (Spark closure)
- `measures: List[Measure]` — each with `SemanticScope => Column`
- `calculatedMeasures: List[CalculatedMeasure]` — CalcGraph (Spark-flavored)
- `joins: List[JoinInfo]` — typed but Spark-flavored
- `filters: List[SemanticFilter]` — predicates (Spark-flavored)
- `rollups: List[Rollup]` — rollup definitions
- `metadata: Map[String, String]`
- **Source: `Dataset<Row>`** — Spark execution state (the crux of the issue)

### `core.Model` (the target shape)

Defined in `semanticdf-core/src/main/scala/io/semanticdf/core/model/Model.scala`. Fields:

- `name: String`, `description: Option[String]`, `version: Int`, `status: ModelStatus`
- `source: SourceRef` (engine-portable reference, NOT a `Dataset`)
- `dimensions: List[Dimension]`
- `measures: List[Measure]`
- `calculatedMeasures: List[CalculatedMeasure]` (engine-portable, Expr-based)
- `joins: List[JoinSpec]`
- `filters: List[FilterSpec]` (Expr-based)
- `rollups: List[RollupSpec]`
- `defaultPolicies: ModelPolicyDefaults`
- `extensions: Map[String, ExtensionValue]`

**Zero Spark imports.** Engine-portable. Pure data.

### The existing bridge (PR #408)

`adapters/semanticdf-spark/src/main/scala/io/semanticdf/ModelBridge.scala` (291 LoC):

```scala
object ModelBridge {
  def toModel(st: SemanticTable): Either[ModelValidationError, Model] = { ... }
}
```

This converts legacy `SemanticTable` → `core.Model` but has known limitations (per its own comments):

1. **Measure aggregate is placeholder `Sum`.** The legacy `Measure.expr: SemanticScope => Column` is a closure; we can't statically determine `Sum`/`Avg`/`Count`. Future work needed.
2. **Dimensions simplified to `Expr.FieldRef(name)`.** Assumes name = source-column. Dimensions whose `expr` aliases a different source column are lost.
3. **Filters NOT converted.** "Predicate type duplication; deferred to v0.5.0."
4. **CalculatedMeasures NOT converted.** "CalcGraph is spark-flavored; deferred to v0.5.0."
5. **Rollups NOT converted.** "RollupSpec is engine-portable but the rollup definitions live in spark-flavored types; deferred to v0.5.0."
6. **No policy extraction.** `defaultPolicies = ModelPolicyDefaults.none`.
7. **No extension extraction.** `extensions = Map.empty`.

**The current MCP engine path uses `ModelBridge.toModel` to produce a real `core.Model` from the legacy table** (per PR #408 follow-up). This means the conversion logic IS exercised today.

## 2. The gap (per `ModelBridge` v1 limitations)

| Field | Currently converted? | Path to v1 conversion |
|---|---|---|
| name, description, version, status | ✅ yes | n/a |
| source | ✅ yes (from `sourceTable`) | n/a |
| dimensions | ⚠️ simplified to `FieldRef(name)` | Detect when name ≠ source-column; emit proper `Expr` |
| measures | ⚠️ placeholder `Sum` aggregate | Detect aggregate from `exprString` hint OR evaluate closure against synthetic scope |
| joins | ✅ yes (with `JoinKind` mapping) | Refine `kind` mapping |
| filters | ❌ no (deferred per the doc) | **Use `PredicateToExprConverter` (PR #418/#419/#420) — this is now available** |
| calculatedMeasures | ❌ no (deferred per the doc) | Convert CalcGraph → Expr-based calculated measures |
| rollups | ❌ no (deferred per the doc) | Convert legacy Rollup → RollupSpec |
| defaultPolicies | ❌ no | Extract from model metadata if present |
| extensions | ❌ no | Extract from model metadata if present |

## 3. The proposed migration

### Why a new portable manifest reader (not just fix `ModelBridge`)

The fundamental issue: `ModelBridge` converts a `SemanticTable` (which holds a `Dataset<Row>`) to a `core.Model`. By the time you have a `SemanticTable`, you've already coupled to Spark.

A **portable manifest reader** reads YAML directly into `core.Model`, bypassing `SemanticTable` entirely. This is the right shape for:
- Engine adapters that don't use Spark (Trino, DuckDB, PostgreSQL, Hera)
- The platform (Restate) — where journaling requires pure data (`SemanticTable.Dataset.rdd` is non-journalable)
- Future engines we don't know about

### The 3-PR sequence

#### PR #A: Portable manifest reader (`core.model.YamlManifestLoader`)

**Goal:** A new reader `core.model.YamlManifestLoader.load(path: Path): Either[ManifestError, List[Model]]` that produces `core.Model` directly from YAML, bypassing `SemanticTable`.

**Scope estimate:** ~500-700 LoC
- 1 new file in `semanticdf-core/src/main/scala/io/semanticdf/core/model/YamlManifestLoader.scala`
- 6-8 new files for portable YAML types (`PortableDimension`, `PortableMeasure`, `PortableCalculatedMeasure`, `PortableJoin`, `PortableFilter`, `PortableRollup`, `PortableStatus`, `PortableModel`)
- 1 new file for `ManifestError` sealed ADT
- 1 new test file: `YamlManifestLoaderSpec`

**Coverage:**
- All 12 fields of `core.Model` are populated
- Uses Jackson YAML (already a transitive dep)
- Uses `Expr` types from `core.expr.Expr` (engine-portable)
- Uses `SourceRef` from `core.model.SourceRef`

**NOT covered in this PR:**
- Legacy YAML format (handled in PR #B)
- Format auto-detection (handled in PR #B)
- dbt/Ossie/SDF bridges (separate concern)

#### PR #B: Dual reader (`legacy vs portable`)

**Goal:** A single entry point that detects the manifest format and dispatches to the right reader:
- Legacy YAML → `SemanticTable` (existing `YamlLoader`)
- Portable YAML → `core.Model` (PR #A's reader)
- Manifests with both legacy AND portable keys → prefer portable, warn on legacy

**Scope estimate:** ~300-500 LoC
- 1 new file: `ManifestFormat` enum + detection heuristic
- 1 new file: `DualManifestReader` that dispatches based on format
- Update MCP server's `Models` to use the dual reader (optional, behind a flag)
- 1 new test file: `DualManifestReaderSpec`

**Backward compat:**
- Existing YAML files (`examples/*/models/*.yml`, 20 files) keep working via the legacy path
- New YAML files use the portable format
- A migration tool can rewrite legacy files to portable (out of scope for this PR)

#### PR #C (optional): Manifest writer + migration tooling

**Goal:** A writer that takes `core.Model` → portable YAML, plus a migration tool that takes legacy YAML → portable YAML.

**Scope estimate:** ~300-500 LoC
- 1 new file: `YamlManifestWriter` (symmetric to the loader)
- 1 new file: `ManifestMigrationTool` (legacy → portable, with human-readable diff)
- Tests + docs

**Trigger conditions for PR #C:**
- At least one user asks to migrate their existing YAML
- OR the dual reader shows the legacy path is exercised often enough that auto-migration makes sense
- OR a third adapter lands that needs portable manifests

If none of these fire, PR #C can wait.

## 4. Per-PR design constraints (9 skills applied)

For each PR in the sequence, the design must satisfy:

- **karpathy §1 (surface assumptions)**: every PR's doc states the design choice, surface tradeoffs, and what's out of scope.
- **karpathy §2 (minimum code)**: don't refactor more than needed. PR #A focuses on the reader; PR #B on the dual dispatch; PR #C on the writer.
- **karpathy §3 (surgical)**: only touch the manifest layer. Don't refactor `SemanticTable` or `ModelBridge` (the legacy bridge continues to serve non-migrated paths).
- **scala-data-driven-refacer §1**: portable YAML types are `case class`/`sealed trait` with no behavior. Behavior lives in the reader.
- **scala-data-driven-refacer §2**: portable YAML types are unconditional (no `require` in the constructor); validity is enforced by `Model.of` (the existing smart constructor).
- **scala-data-driven-refacer §3**: portable YAML format is a closed, known-at-compile-time case set. NOT config-driven → no Map dispatch.
- **scala-jvm-safety**: portable manifest types are pure data. No resources opened. No threads.
- **scala-error-handling §1**: public API returns `Either[ManifestError, Model]`. `ManifestError` is a sealed ADT with SPECIFIC cases (per §4 hard ban #1 — no `Either[String, _]`).
- **scala-impact-analysis**: each PR is additive. Existing `YamlLoader` keeps working. Existing tests don't break. New tests prove the new path.
- **scala-perf-testing**: portable reader is one-shot (manifests are small). No hot path. No benchmark needed.
- **scala-spark-batch-bugs**: portable YAML types must be Spark-serializable (since `core.Model` flows through Spark in the v0.3.0+ world). Use `extends Product with Serializable` (already the pattern in `core.model`).
- **scala-jar-packaging**: no new dependencies. Jackson YAML is already a transitive dep via Jackson.

## 5. Migration path

The user-facing migration path:

1. **Authors of new manifests**: write in the portable format from day 1.
2. **Existing manifest authors**: keep using the legacy format. The dual reader handles both.
3. **When to migrate a legacy manifest**: when the user wants to use a non-Spark engine adapter (Trino, DuckDB, PostgreSQL, Hera, etc.). The `ModelBridge` already produces a `core.Model` from legacy `SemanticTable` (with the documented limitations); new engines can use that.
4. **When to fix `ModelBridge` limitations**: when a limitation actually bites a real user (per "build to learn, then extract"). We don't pre-emptively fix the Measure aggregate detection if no one has asked.

## 6. Open questions

These should be resolved BEFORE the first implementation PR (PR #A):

1. **Format choice**: Is the portable manifest YAML (matches existing examples) or JSON (matches `manifest.schema.json`)? YAML is more human-friendly; JSON has better schema validation tooling. **My recommendation: YAML** (matches the existing format and examples).

2. **Schema validation**: Do we ship a JSON Schema for the portable YAML? The existing `manifest.schema.json` is for the legacy format. A portable schema would let users validate before publishing. **My recommendation: yes, ship a schema as part of PR #A**.

3. **Expr serialization**: How do portable YAML files represent `core.expr.Expr`? The current legacy format uses raw SQL strings (e.g., `expr: "origin IS NOT NULL"`). The portable format could:
   - Use raw SQL strings + `Expr.SqlString(s)` (simplest, matches legacy)
   - Use structured `Expr` types (typed, but verbose)
   **My recommendation: raw SQL strings for v1** (matches legacy, simplest migration). Structured `Expr` can land later if needed.

4. **Status enum mapping**: Legacy uses `"draft" | "published" | "deprecated"`. `core.ModelStatus` is a sealed ADT with `Draft`, `Published`, `Deprecated`. The portable format should use the same string values (matches legacy wire format).

5. **Rollup format**: Legacy has complex rollup definitions. `core.RollupSpec` has a typed shape. Do we use raw YAML (legacy-compatible) or typed? **My recommendation: raw YAML for v1, typed via `YamlManifestLoader` later**.

## 7. Recommended execution order

Given the user's preference for "build to learn, then extract" + minimum-code-that-solves-the-problem:

1. **PR #A (portable reader)**: ~500-700 LoC. Land this first. Validates the portable format.
2. **PR #B (dual reader)**: ~300-500 LoC. Land after PR #A is reviewed. Validates backward compat.
3. **PR #C (writer + migration tool)**: ~300-500 LoC. ONLY if a real user needs it. Defer otherwise.

Total: ~1,200-1,700 LoC across 2-3 PRs. Matches the audit's estimate of ~1,200-1,500 LoC.

## 8. Out of scope for this design

- **Migrating existing example YAML files**: they're in the legacy format. They keep working via the dual reader.
- **Refactoring `SemanticTable`**: it's the legacy shape. It works. Don't refactor it.
- **Refactoring `ModelBridge`**: it works for the v0.3.1 MCP path. Limitations are documented. Fix the limitations when a real user needs them.
- **dbt/Ossie/SDF bridge migration**: those adapters already produce `SemanticTable`. Migrating them to produce `core.Model` is a separate concern.
- **Schema migration tools**: out of scope until a real migration is needed.

## 9. Trigger conditions for revisiting this design

1. A non-Spark engine adapter (Trino, DuckDB, etc.) needs to consume a YAML manifest directly. Today they go through `ModelBridge` (limitations accepted).
2. A user complains about `ModelBridge`'s limitations (placeholder Sum, missing filters, missing calculatedMeasures).
3. The platform (Restate) needs to journal models — currently blocked by `Dataset.rdd` per the audit.
4. A new "Manifest v3" requirement emerges (e.g., a new field type).

When any of these fire, revisit this doc and start with the first unimplemented PR.
