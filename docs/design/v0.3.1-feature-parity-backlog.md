# v0.3.1 feature-parity backlog

**Status:** Pre-v0.3.0 snapshot. Captures the gaps between the v0.3.0
multi-engine portable design and full feature parity with the legacy
Spark library (`io.semanticdf.SemanticTable`). Each gap names the
specific file(s) and the work item that closes it.

This is a **gap analysis**, not a design exploration. For the
multi-engine design itself, see [`docs/design/multi-engine-design.md`](multi-engine-design.md).
For the type-safety backlog, see [`docs/backlog-type-safety.md`](../backlog-type-safety.md).
For the *current* scope and workarounds, see [`docs/known-limitations.md`](../known-limitations.md).

## At a glance

| # | Gap | Severity | Closes in |
|---|---|---|---|
| 1 | `SparkEngineProvider` bypasses portable `Model.compile`; queries flow through legacy `SemanticTable` | HIGH | v0.3.1 PR "SparkEngine → portable pipeline" |
| 2 | No `Expr.All` (percent-of-total / `t.all`) in portable `Expr` ADT | HIGH | v0.3.1 PR "Expr.All + per-engine lowerer" |
| 3 | Joins deferred in `TrinoQueryCompiler` ("`-- Joins deferred to a future PR`" comment) | HIGH | v0.3.1 PR "Trino + DuckDB join compile" |
| 4 | Predicate type split: legacy `io.semanticdf.predicate.Predicate` vs portable `core.predicate.Predicate`; `ModelBridge` silently drops filters | HIGH | v0.3.1 PR "Predicate unification + ModelBridge full conversion" |
| 5 | `DuckDBQueryCompiler` missing aggregates (Stddev / Variance / Median / Percentile) | MEDIUM | v0.3.1 PR "DuckDB aggregate coverage" |
| 6 | No engine implements `RollupSpec` compile (modeled portably but execution is Spark-only) | MEDIUM | v0.3.3+ |
| 7 | No engine implements `CatalogAdapter` (modeled portably; UC / HMS adapters are `SourceResolver` only) | LOW | v0.3.3+ |

Not in this backlog (legacy-only features with no portable equivalent; gated on consumer demand, not in scope for v0.3.1):

- Structured Streaming / windowed totals (the legacy `StreamingSupport` lives only in `adapters/semanticdf-spark`).
- Typed columns / phantom types (`io.semanticdf.SemanticField[T]`) — already covered by [`docs/backlog-type-safety.md`](../backlog-type-safety.md).
- Window functions / Transforms (legacy `withWindow`, `withTransforms`) — not modeled in portable; future ADR.
- Spark tuning knobs (`withMaterialize`, `withSalt`, `withBroadcastJoinThreshold`) — partially covered by `EngineContext.policy`; remainder stays Spark-only.

## Engine × feature matrix

What's already exercised by which engine adapter, against the v0.3.0
portable contract.

| Feature | Spark (`SparkEngineProvider`) | Trino (`TrinoEngine`) | DuckDB (`DuckDBEngine`) |
|---|---|---|---|
| `compile(Model)` portable path | ❌ uses legacy `SemanticTable` | ✅ → `ExecutionPlan[Any]` | ✅ → `ExecutionPlan[Any]` |
| `compile(RelOp)` portable IR | ❌ | ✅ | ✅ |
| Aggregates (Sum / Count / Avg / Min / Max) | ✅ legacy | ✅ SQL | ✅ SQL |
| Stddev / Variance | ✅ legacy | ✅ SQL | ❌ missing |
| Median / Percentile{Continuous,Discrete} / ApproxPercentile | ✅ legacy | ✅ SQL | ❌ missing |
| Joins (Inner / Left / Right / Full / Cross) | ✅ legacy | ⚠️ rendered but **deferred** | ⚠️ rendered |
| Filters (where / having) | ✅ legacy | ✅ | ✅ |
| `t.all` / percent-of-total | ⚠️ `SemanticScope.all` throws `UnsupportedOperationException` (per `Scope.scala`) | ❌ | ❌ |
| Sort / Limit / Offset | ✅ legacy | ✅ | ✅ |
| Rollups | ✅ legacy `RollupQuery` / `RollupRegistry` | ❌ not implemented | ❌ not implemented |
| Streaming (Structured Streaming) | ✅ legacy `SemanticTableStreaming` | ❌ | ❌ |
| Materialize / Salt / Broadcast hint | ✅ legacy fluent | ⚠️ `EngineContext.materializePolicy` only | ⚠️ capability-only |
| Audit / Cache (`withAuditSink`, `withResultCache`) | ✅ legacy fluent | ⚠️ `EngineContext` covers audit + cache | ⚠️ same |
| Window functions (`withWindow`) | ✅ legacy | ❌ | ❌ |
| Transforms (`withTransforms`) | ✅ legacy | ❌ | ❌ |
| Typed columns (`SemanticField[T]`) | ✅ legacy | ❌ | ❌ |
| Catalog identity + CAS (`CatalogAdapter`) | ❌ (modeled; no implementation) | ❌ | ❌ |

The portable **shape** for every row is complete in `semanticdf-core/`.
The portable **execution** is partial — the gap between "modeled" and
"implemented by all engines" is what this backlog tracks.

## Gap-by-gap detail

### Gap 1 — `SparkEngineProvider` bypasses portable `Model`

**Where:** `adapters/semanticdf-spark/src/main/scala/io/semanticdf/spark/SparkEngineProvider.scala`

**Current behavior (per the doc comment at lines 38-46):**

```scala
override def query(
    model:   io.semanticdf.core.model.Model,
    request: MCPQueryRequest,
    ctx:     EngineContext,
): Either[EngineError, PortableQueryResult] = {
  // The Spark provider currently uses the legacy
  // `SemanticTable` path (per the existing Query handler).
  // For v1, the MCP `Model` lookup is done by name in the
  // spark adapter's table registry. The `request.model` is
  // the name; we look it up in the spark registry.
  sparkTableRegistry.get(request.model) match {
    case None => Left(EngineError.ModelNotFound(request.model))
    case Some(table) => runQuery(table, request)
  }
}
```

The `Model` parameter is accepted but only `request.model` (the name
string) is used. The actual execution goes through
`runQuery(table, request)` where `table: SemanticTable` is the legacy
fluent type — bypassing `compile(Model)` entirely.

**Why it matters:** Spark is the canonical adapter. If it doesn't
exercise the portable path, the v0.3.0 contract has no production
consumer for Spark. The portable types are "correct on paper" but
unverified against real Spark workloads.

**Closes in:** A PR that routes `SparkEngineProvider.query` through
`compile(model)` (or the `compile(RelOp)` overload) instead of
`runQuery(table, request)`. Reuses the existing
`SparkEngineProvider.runQuery(table, request)` body but with the
portable plan.

### Gap 2 — No `Expr.All` in portable `Expr` ADT

**Where:** `semanticdf-core/src/main/scala/io/semanticdf/core/expr/Expr.scala`

**Current state:** `Expr` has 20 cases — `Literal`, `FieldRef`,
`MeasureRef`, the 5 arithmetic ops, 6 comparisons, `And`/`Or`/`Not`,
`IsNull`/`IsNotNull`, `FunctionCall`. There is **no** `All(measureName: String)`
case for percent-of-total / `t.all(name)`.

**Legacy status:** `SemanticScope.all(name)` in
`adapters/semanticdf-spark/src/main/scala/io/semanticdf/Scope.scala`
already throws `UnsupportedOperationException` — the doc comment
says it "is only valid inside a `groupBy(...).aggregate(...)`, where
percent-of-total can be computed." So the legacy library has the
*surface* but not the *implementation*. Portability makes the gap
visible; it doesn't cause it.

**Closes in:** A PR that adds
`final case class All(measureName: String) extends Expr` to the
portable `Expr` ADT, then a per-engine lowerer:
- Spark: `F.sum(...) over Window.partitionBy() / F.sum(...) over ()`
- Trino: `SUM(...) / SUM(...) OVER ()` (already supported in Trino's SQL)
- DuckDB: same `OVER ()` syntax

Then `SparkEngineProvider` can route the new case through the
`compile(Model)` path (per Gap 1).

### Gap 3 — Joins deferred in `TrinoQueryCompiler`

> **Closed in this PR (v0.3.1 Gap 3 closure).** `compileRelOp` now
> accepts a `modelSources: Map[String, SourceRef]` parameter and
> emits JOIN clauses for hand-built `RelOp.Join` plans.

**Where:** `adapters/semanticdf-trino/src/main/scala/io/semanticdf/trino/TrinoQueryCompiler.scala`

**Closed by:** `feat/v0.3.1-trino-relop-join` branch.

**What changed:**
1. `TrinoQueryCompiler.compileRelOp(plan, modelSources = Map.empty)`
   signature extended. Engine-level callers (`TrinoEngine`) updated
   to pass `Map.empty` (the engine-level path doesn't construct
   hand-built `RelOp.Join` plans; joins flow through `compile(model,
   modelSources, ...)`).
2. `renderRelOp` recursively threads `modelSources`. The `RelOp.Join`
   case now: extracts the right-side `RelOp.Scan` source, validates
   it against `modelSources`, picks the SQL JOIN keyword from
   `JoinKind`, and renders the ON clause (single-key equality only —
   multi-key joins deferred to v0.4.0).
3. `DuckDBQueryCompiler.compileRelOp` mirrors the signature for API
   parity, with a doc comment noting the synthetic-Model path
   doesn't currently emit JOIN clauses (use Trino for hand-built
   RelOp plans with joins).
4. New tests:
   - `TrinoRelOpJoinSpec` — 4 tests (Inner / Left / Cross / missing
     source).
   - `TrinoQueryCompilerSpec` — replaces the old fail-loud
     regression test with two new tests (success path + new
     fail-loud message).
5. Per scala-data-driven-refactor §1: `RelOp.Join` is shape-only
   data; the body (right-side source lookup) lives in the
   adapter. Per scala-jvm-safety §1: typed `Either[EngineError, X]`,
   no `null` returned (uses `Option` at the helper level).
6. Multi-key joins (an `AND`-chained condition) fall back to no ON
   clause — documented limitation; v0.4.0 work.

**Why it matters:** Closes a gap that was deferred from v0.3.0
because the IR-level RelOp.Join doesn't carry the right-side table.
The fix follows the v0.3.1 design principle: **data in core,
behavior in adapter** — the join EMISSION is engine-specific SQL,
the JOIN KIND / CONDITION is portable data.

### Gap 4 — Predicate type split + `ModelBridge` silently drops filters

**Where:**
- `adapters/semanticdf-spark/src/main/scala/io/semanticdf/predicate/Predicate.scala` (legacy)
- `semanticdf-core/src/main/scala/io/semanticdf/core/predicate/Predicate.scala` (portable)
- `adapters/semanticdf-spark/src/main/scala/io/semanticdf/ModelBridge.scala` (the bridge)

**Current state:** The legacy `Predicate` and portable
`core.predicate.Predicate` have parallel case classes (`Eq`, `Ne`,
`Lt`, ..., `And`, `Or`, `IsNull`, `In`). They are separate types —
neither extends nor converts to the other. The `ModelBridge.toModel`
scaladoc explicitly states (per the v0.3.0 PR review comment):

> 4. **Filters (Predicate) are dropped.** The legacy Predicate type is
>    spark-flavored; the engine-portable Predicate is a separate,
>    parallel type. A converter is required; deferred to v0.5.0.

**Why it matters:** Every legacy `SemanticTable.where(...)` clause is
silently lost when converting to the portable `Model`. A user who
migrates from legacy to portable and forgets to also add filters
manually to the portable side gets *correct but unsanitized* queries.

**Closes in:** A PR that:
1. Adds a `PredicateConverter.toPortable(legacy: io.semanticdf.predicate.Predicate): io.semanticdf.core.expr.Expr` (the portable `Expr` covers all the legacy operations).
2. Wires `ModelBridge.toModel` to call the converter on every `SemanticTable.where`.
3. Adds round-trip tests (`toPortable(toPortable(x)) == toPortable(x)`).

### Gap 5 — DuckDB missing aggregates

**Where:** `adapters/semanticdf-duckdb/src/main/scala/io/semanticdf/duckdb/DuckDBQueryCompiler.scala`

**Current state:** The compiler maps `Sum`, `Count`, `CountDistinct`,
`Avg`, `Min`, `Max` — but **not** `Stddev{Sample,Population}`,
`Variance{Sample,Population}`, `Median`, `Percentile{Continuous,Discrete}`,
`ApproxPercentile`, `First`, `Last` (6 of 16 `AggregateFn` cases
shipped; 10 missing).

**Why it matters:** A portable `Model` carrying advanced aggregates
fails the DuckDB engine at compile time. Same portable model works
on Trino and Spark; portability is broken for DuckDB.

**Closes in:** A short PR that adds the 10 missing `AggregateFn`
cases to `DuckDBQueryCompiler`. Trino already has them (verified in
`TrinoQueryCompiler`).

### Gap 6 — No engine implements `RollupSpec` compile

> **Closed in this PR (v0.3.1 Gap 6 closure).** `DuckDBQueryCompiler.compile`
> now mirrors `TrinoQueryCompiler.compile`: selects a covering fresh
> rollup at compile time, substitutes the FROM clause with the
> rollup's `SourceRef`, and prepends `-- using rollup '<name>'`.

**Where:** `adapters/semanticdf-duckdb/src/main/scala/io/semanticdf/duckdb/DuckDBQueryCompiler.scala`

**Closed by:** `feat/v0.3.1-duckdb-rollup-compile` branch.

**What changed:**
1. `DuckDBQueryCompiler.compile` signature extended to
   `(model, modelSources, rollupSources, rollupWatermarks, now)`,
   matching the v0.3.0 Trino compiler. All new params default
   to empty / `Instant.now()`, preserving the 3-arg backward-
   compatible call sites (e.g. `DuckDBEngine.compile`).
2. New private helpers `selectRollup` + `isFresh` mirror
   `TrinoQueryCompiler` exactly. The selection logic (coverage
   check + freshness check + source-map lookup) is engine-
   portable in shape — only the FROM-clause substitution is
   engine-specific.
3. `effectiveSource` + `rollupComment` substitution at the top
   of `compile` (lines ~85-94). When a rollup is selected, the
   comment is prepended to the SELECT list.
4. New tests in `DuckDBRollupCompileSpec` (7 tests): NoTracking
   substitution, rollup-name comment, fresh-watermark Track,
   stale-watermark + FallBackToBase, missing-watermark stale,
   no-rollups-in-model, backward-compat 3-arg signature.
5. Per scala-data-driven-refacer §3 (sealed ADT over Map):
   `RollupFreshnessSpec` (`NoTracking` / `Track(maxStaleness, onStale)`)
   and `OnStalePolicy` (`FallBackToBase` / `Error`) are
   exhaustively matched. Per scala-jvm-safety §1: typed
   `Option[(RollupSpec, SourceRef)]` for "may not exist"
   (the rollup-map lookup).
6. **No source-side breaking changes.** The pre-v0.3.1 3-arg
   signature continues to work (existing `DuckDBEngine.compile`
   call site unchanged). All 53 DuckDB tests pass.

**Behavior consistency (Trino vs DuckDB):**
- Selection rules identical (`selectRollup` + `isFresh` are
  mechanical copies).
- Source substitution identical (`effectiveSource` pattern).
- Comment format identical (`-- using rollup '<name>'`).
- Error handling: silent fall-back to base (consistent with
  Trino's existing `OnStalePolicy.Error` behavior — both
  silently fall back; surface the `Error` policy is a v0.4.0
  follow-up that closes the asymmetry).

**Why it matters:** Rollups are a v0.2.4 feature pillar. A portable
`Model` declaring rollups now compiles on Spark (via legacy path),
Trino (per PR #418), AND DuckDB (per this PR). A user moving
between engines keeps their rollup optimization with the SAME
selection semantics — no engine-specific YAML.

### Gap 7 — No engine implements `CatalogAdapter`

**Where:** `semanticdf-core/src/main/scala/io/semanticdf/core/catalog/CatalogAdapter.scala` (modeled portably); `adapters/semanticdf-unity-catalog/`, `adapters/semanticdf-hive-metastore/` (resolve sources only).

**Current state:** `CatalogRef`, `CatalogIdentity`, `PublishMode`
(`CreateOnly` / `Upsert` / `CompareAndSet`), `PublishResult`,
`CatalogError` are all in `core/catalog/`. The Unity Catalog and Hive
Metastore adapters implement `SourceResolver` (resolve a `SourceRef`
to a concrete source) but **not** `CatalogAdapter` (publish a model /
rollup with per-identity atomic CAS).

**Why it matters:** The v0.3.0 release notes promise a
"Catalog identity + CAS publication contract" but no production
adapter implements it. A user who tries to call `publish()` on the
UC or HMS adapter hits an `UnsupportedOperationException` or
`NotImplementedError` (depending on the adapter).

**Closes in:** A PR per catalog adapter that implements the
`CatalogAdapter` trait. This is gated on consumer demand (most
`SemanticTable` users read from a YAML directory, not from a UC
publishing endpoint). **Defer to v0.3.3+ unless a consumer signals demand.**

## Recommended ordering for v0.3.1

Following the user's "most valuable to have, not garbage or little
cosmetic" principle, the priority order is:

| Priority | Gap | Why this order |
|---|---|---|
| **P0** | #1 (Spark → portable) | Without this, no production consumer validates the v0.3.0 contract end-to-end. |
| **P1** | #4 (Predicate unification) | Blocks any consumer that uses `where()` clauses. Silent data loss is a CRITICAL bug. |
| **P1** | #2 (`Expr.All` + per-engine lowerer) | Restores a documented feature (pct-of-total). Closes a v0.3.0 design omission. |
| **P2** | #3 (Trino / DuckDB joins) | Restores core SQL capability that was supposed to ship with the engine. |
| **P2** | #5 (DuckDB aggregates) | Short PR; closes an obvious parity gap. |
| P3 | #6 (Rollup compile) | Defer to v0.3.3 unless consumer demand. |
| P3 | #7 (Catalog adapter impl) | Defer to v0.3.3 unless consumer demand. |

P0 + P1 = ~3-5 PRs of substantive work that closes the most painful
gaps. P2 = ~2 PRs of mechanical work (the lowerers already have the
right shape). P3 = gated on consumer signal.
