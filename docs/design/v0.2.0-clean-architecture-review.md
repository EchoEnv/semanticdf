# Clean-Architecture Review (v0.2.0 — SemanticTable split)

**Scope**: target the v0.2.0 refactor — specifically the planned `SemanticTable.scala` split.
**Date**: this session.
**Method**: dependency graph via SocratiCode (1006 chunks, 169 files, 38 edges), per-file read of `SemanticTable.scala`, blast-radius grep across 81 files.

> **Mantra:**
> 1. **The dependency rule is the only rule.**
> 2. **Data outlives layers.**
> 3. **Every boundary has a price.**
> 4. **Follow the data across the boundary.**
> 5. **Purity is not the deliverable.**

## 0. Domain

This is a **library** — no DAGs, no orchestrators, no streaming jobs. The "data" is
YAML manifests + DataFrames; the "transformations" are the op tree (`SemanticOp`).
It has a streaming terminal (`toStreamingQuery`) but the streaming logic is a
short-circuit around the batch op tree, not a stateful Flink/Kafka bean.

So the review is closer to "library with a request/response or command model" than
to DE/streaming. The data-engineering and streaming reference files don't apply
directly. We judge the boundary audit and the data shape.

## 2. Data model

The shape that flows through `SemanticTable` is:
- **A `SemanticOp` tree** (case class hierarchy, ~16 op types) — the "data."
- **An immutable `SemanticTable` wrapper** carrying the tree plus metadata
  (`version`, `sourceTable`, `status`, `auditSink`, `auditRequest`, `resultCache`).
- **Terminals** compile the tree to a `DataFrame` or `StreamingQuery`.

The data flow in a typical query:
```
SemanticTable (root: SemanticOp)
  ↓ .query(req)
SemanticTable (root: SemanticOp, auditRequest: Some(req))
  ↓ .limit(10)
SemanticTable (root: SemanticOp, auditRequest: Some(req))
  ↓ .toDataFrame(spark)
AuditSink.emit(event with rowCount, elapsedMs, ...)
  → DataFrame
```

The `auditRequest` is captured at `query()` and **preserved through the fluent
chain** — every builder method returns a new `SemanticTable` with the same
`auditRequest`. Same for `auditSink`, `resultCache`, `sourceTable`, `version`,
`status`. Six fields that get threaded through every copy.

## 3. Boundary audit

| # | Boundary | Class | Reasoning |
|---|---|---|---|
| 1 | `SemanticTable` ↔ `SparkSession` | **Earning its keep** | The Spark session is the volatile dependency. Wrapping it is the public API. |
| 2 | `SemanticTable` ↔ `Op tree (SemanticOp)` | **Earning its keep** | The op tree is the data; the boundary is the deferred-compilation contract. |
| 3 | `SemanticTable` ↔ `AuditSink` | **Earning its keep** | Audit is a side-effect that's deliberately opt-in via a seam. |
| 4 | `SemanticTable` ↔ `ResultCache` | **Earning its keep** | Cache is opt-in via a seam, same reasoning. |
| 5 | `SemanticTable` ↔ `StreamingQuery` | **Earning its keep** | The streaming terminal is the right place to bridge batch op tree + Spark streaming. |
| 6 | `SemanticTable` ↔ `Model` (manifest) | **Earning its keep** | The manifest is the YAML schema; the boundary is the loader's responsibility. |
| 7 | `SemanticTable.scala` (the file!) | **Misplaced** | The file is a **god object** — 80 methods on 4 different concerns. Not a clean-architecture violation of the dependency rule, but a code-organization issue. |

## 4. The finding that v0.2.0 targets

**Finding 1 — `SemanticTable.scala` is a god object.** (Medium severity from the
v0.1.17 review, but upgraded to High here because the threshold is concrete.)
- 3341 lines
- 80 public methods
- 8 distinct responsibilities (terminals, query builder, mutation, introspection, schema, streaming, audit/cache, rendering)
- 12 explicit section markers (`// ----- ... -----`) — the file already knows it's many things

Smell tests:
- **Single Responsibility Principle**: a single class with 80 methods spanning 8 concerns. Any one developer working on streaming has to scroll through groups and aggregates; any one working on groups has to scroll past audit and cache.
- **Cognitive load**: the file is 3341 lines. A reader has to track which section they're in mentally.
- **Co-change coupling**: streaming internals (lines 351-689) and audit/cache setters (lines 1076-1111) are modified independently. The two have nothing in common except that they live on the same class.
- **Diff-friendliness**: a single-line change to `toStreamingQuery` produces a 3341-line diff in PR review.

**Why this isn't Critical**:
- The dependency rule is satisfied — `SemanticTable` is the right boundary.
- The class is a single class, so consumers aren't fragmented.
- Tests pass. The code is correct.

**Why this is High** (not just Medium):
- The threshold is concrete: 80 methods, 3341 lines, 8 sections.
- The structure is already built into the file (section markers) — we just need to follow them.
- The refactor is mechanical: same methods, same signatures, same behavior, just grouped into 4 files.

## 5. Findings by severity

### Critical

**None.** No dependency-rule violations. No data-loss risk. No silent-failure paths.

### High

**Finding H1** — `SemanticTable.scala` is a god object (80 methods, 3341 lines, 8 sections).
- **Cost**: cognitive load, review friction, co-change coupling.
- **Benefit of fix**: 4 smaller files, each ~800 lines, each with one responsibility.
- **Risk of fix**: mechanical — same methods, same signatures, same behavior.
- **Disclosed gap**: SocratiCode says 3 explicit importers, but `SemanticTable` is also accessed via package-local access from 78 other files. The split keeps `SemanticTable` as the same class, so all 78 paths keep working. The split is internal file organization, not a class split.

### Medium

**Finding M1** — The 6 fluent-state fields (`version`, `sourceTable`, `status`, `auditSink`, `auditRequest`, `resultCache`) are threaded through every builder method by name. 77 call sites of `new SemanticTable(...)`.
- **Already mitigated by**: the case-class copy mechanism (every builder does `this.copy(...)`). The fields are self-documenting.
- **NOT recommending fixing in v0.2.0**: structuring these into a runtime "metadata" sub-class would require changing the public API. The current threading is fine; it's just verbose.

### Low

**Finding L1** — `Scope`, `SortKey`, `ValidationResult`, `JoinInfo`, `MeasureKind`, `SemanticFilter`, `SemanticGroupBy`,
`All` case classes are all defined in `SemanticTable.scala` but are not really
"part of SemanticTable." They should live in their own files.
- **Cost**: minor — these are PUBLIC types, so moving them requires touching every importer.
- **Risk**: low — pure code movement, no logic change.
- **Recommendation**: defer to v0.2.x as a cleanup once the main split lands.

## 6. The v0.2.0 split plan

The file already has 12 section markers. The natural split is:

| File | Lines | Methods | Concern |
|---|---|---|---|
| `SemanticTable.scala` | 91–830 (core) + 2060–2646 (internals) | ~25 | Core class declaration, terminals (`toDataFrame`, `execute`), fluent builders (`query`, `where`, `having`, `orderBy`, `limit`, `withHint`, `withRowFilter`, `atTimeGrain`), group-by, schema, introspection, and internal helpers. |
| `SemanticTableStreaming.scala` | 831–753 (sections at 831, 833) | ~10 | `toStreamingQuery` (3 overloads), `findStream`, `findStreamingDimensions`, `substituteStreamingLeaf`, `findStreamRecursive`, `emitStreamingAudit`. |
| `SemanticTableMutation.scala` | 1227–1922 (sections at 1227, 1571, 1872, 1919) | ~15 | `withDimensions`, `withMeasures`, `withTransforms`, `join_one`, `join_on`, `join_many`, `join_many_on`, `join_cross`, `where`, `having`, `orderBy`, `limit`. |
| `SemanticTable.scala` (collect‑only) | 2053–2062, 2727–3341 | ~10 | `collectAs`, `queryAs`, `filters`, `allFilters`, `allRowFilters`, `allMeasures`, `allDimensions`, `allJoins`, `allTableNames`, `render`, `SemanticPlanRenderer`. |

Wait — the section markers don't align cleanly to 4 files. Let me re-examine.

Actually the cleanest split is:

| File | Methods | Concern |
|---|---|---|
| `SemanticTable.scala` (core) | ~25 | Core declaration + terminals + query/builder + group-by + introspection + schema |
| `SemanticTableStreaming.scala` | ~10 | Streaming terminals + streaming internals |
| `SemanticTableMutation.scala` | ~15 | Dimension/measure/transform/join builders + filter/sort/limit |
| `SemanticTableCollection.scala` | ~10 | `collectAs`, `queryAs`, `render`, `SemanticPlanRenderer`, `allFilters`, etc. |

The 4-file split keeps each file under 1000 lines and gives each file one
coherent responsibility. The class stays one Scala class — only the file
boundary changes. Consumers don't change.

### Constraint: one Scala class, one file

Important: the split is **file-level only**, not class-level. `SemanticTable`
remains a single class with all 80 methods. The methods are distributed across
files using the **package object** or **implicit class** pattern.

The cleanest mechanism in Scala 2.13 is to put each method in an `object`
or use `implicit class`-style extension. But `SemanticTable`'s methods are
**instance methods** (`def toDataFrame`, not `def toDataFrame(t: SemanticTable)`),
so we can't use implicit classes.

Instead, the split uses **package-private classes**:
- `SemanticTable.scala` declares the class.
- `SemanticTableStreaming.scala` defines methods as `private[semanticdf] class
  SemanticTableStreaming(val self: SemanticTable)` — but this is over-engineered.

**Better**: keep the class declared in `SemanticTable.scala` and use **early
definitions** or **partial classes** — but Scala doesn't have partial classes.

**Best**: keep the class as-is in one file, but extract the **streaming-specific
op-tree walker helpers** (`findStream`, `findStreamRecursive`, `substituteStreamingLeaf`,
`emitStreamingAudit`, `findStreamingDimensions`) into a companion
`SemanticTableStreaming.scala` file that itself contains a `class SemanticTableStreaming(val self: SemanticTable) extends AnyVal` or similar.

Actually — the cleanest approach is **a "facet" object pattern**:

```scala
// SemanticTable.scala
final class SemanticTable private[semanticdf] (...) {
  // Core methods: toDataFrame, execute, query, where, having, orderBy, limit, 
  // withHint, withRowFilter, withAuditSink, withResultCache, 
  // withDimensions, withMeasures, withTransforms, joins, 
  // groupBy, groupByDimensions, aggregate, aggregateMeasures,
  // introspection, schema, validation, etc.
}

// SemanticTableStreaming.scala
final class SemanticTableStreaming(val self: SemanticTable) extends AnyVal {
  def toStreamingQuery(opts: ...): StreamingQuery = ...
  def findStream(op: SemanticOp): Option[DataFrame] = ...
  // ... streaming internals
}

object SemanticTable {
  implicit class Streaming(val self: SemanticTable) extends SemanticTableStreaming(self)
}
```

Wait — `extends AnyVal` doesn't work for a class with a `val` parameter. Use just a regular class with implicit conversion.

Actually, the simplest pattern that PRESERVES the public API exactly:

```scala
// SemanticTable.scala
final class SemanticTable private[semanticdf] (...) {
  // All 80 methods stay here.
  // The file is no longer 3341 lines because we move most of the BODY out 
  // to extension traits, but the methods are still declared on SemanticTable.
}

// In separate file:
package io.semanticdf
trait SemanticTableStreamingOps { self: SemanticTable => ... }
trait SemanticTableMutationOps { self: SemanticTable => ... }
```

This is the **"add trait, mix in"** pattern. Each trait defines a chunk of
methods. `SemanticTable` mixes in all of them. The methods are still on
`SemanticTable` (no caller-side change), but the trait is in a separate file.

**This is the right split.** It preserves the public API 100%, distributes the
code across 4 files, and each file has one concern.

### Final structure

```
SemanticTable.scala           — class declaration + telescopes into traits
SemanticTableCore.scala       — trait with terminals, query, schema, introspection
SemanticTableMutation.scala   — trait with builder methods (where, having, ..., joins, withDimensions, withMeasures, withTransforms)
SemanticTableStreaming.scala  — trait with toStreamingQuery + streaming internals
SemanticTableCollection.scala — trait with collectAs, queryAs, render, SemanticPlanRenderer, allFilters, allMeasures, etc.
```

Each file is ~600-800 lines. Each trait has one concern. The class declaration
in `SemanticTable.scala` is just:
```scala
final class SemanticTable private[semanticdf] ( /* same constructor */ ) 
  extends SemanticTableCore
  with SemanticTableMutation
  with SemanticTableStreaming
  with SemanticTableCollection
```

Public API: **unchanged**.

## 7. What I am NOT recommending

- **Splitting `SemanticTable` into multiple classes**. The class is the right boundary. The methods are intrinsically packaged with the class.
- **Inverting the `core → audit` dependency**. The cost exceeds the benefit (per v0.1.17 review).
- **Moving the case classes (`SortKey`, `ValidationResult`, `JoinInfo`, `MeasureKind`, `SemanticFilter`, `SemanticGroupBy`, `All`) out of `SemanticTable.scala`**. These are public types; moving them requires touching every importer. Defer to v0.2.x.
- **Threading the 6 fluent-state fields through a metadata sub-class**. Would change the public API. The current threading is fine.

## 8. Verification

For **each** trait extraction:
- All 703 lib tests pass.
- `mvn compile` succeeds.
- `mvn test-compile` succeeds.
- The public API (`SemanticTable`'s method signatures) is unchanged.
- The trait can be tested in isolation if it's a streaming internals trait (extracted to a small test if helpful).

If a single trait extraction is too large to verify, split it into 2-3 sub-PRs
within the same v0.2.0 series.

## 9. Disclosure

- **SocratiCode graph is incomplete** — it tracks explicit imports, not package-local access. I supplemented with grep, which found 81 files referencing `SemanticTable`. The 78 non-explicit-importer files (mostly tests, examples, MCP handlers) are all package-local; they don't import `SemanticTable` because they live in the same package. The split is internal, so none of them need to change.
- **Trait-based split is a public-safe refactor** — traits mixed into a class don't add new symbols to the public API. They're an implementation detail. No consumer needs to know.
- **The 4-file split is the recommendation**, but the user can choose 2 or 3 files. Smaller split = lower risk, smaller split = less benefit. The 4-file split is the sweet spot.
