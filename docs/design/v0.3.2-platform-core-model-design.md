# Design: Platform → `core.Model` migration

**Status:** v1 — analytical. No code changes. The design doc + sub-PR plan is the deliverable.

**Version assumption: v0.3.2** (per user's correction — this is part of the v0.3.x minor-release series, not v0.4.0).

**The TL;DR:** `semanticdf-platform` currently uses the Spark-coupled `SemanticTable` type throughout. The platform has a *workaround* pattern (resolve `SemanticTable` fresh on each handler invocation, journal the workaround boundaries explicitly) that **avoids** the `Dataset.rdd` journal-safety problem. Migrating to `core.Model` is a **clean-up + enable** migration that:

1. **Removes the workaround burden** (no more "compile in handler scope, not in Restate.run")
2. **Enables future use cases** where the model itself IS journaled (cross-handler state, lineage-by-version tracking, etc.)
3. **Aligns with the engine-portable goal** (per the v0.3.2 design doc)

Estimated total: ~1,500-2,500 LoC across 4 sub-PRs over multiple sessions.

---

## 1. Current state — what the platform uses

### `SemanticTable` usage by file (8 main files)

| File | Use of `SemanticTable` |
|---|---|
| `model/ModelService.java` | Compile + register path; passes `compiled: SemanticTable` into `HotReloadingModelRegistry.register` |
| `query/QueryService.java` | Resolve model per handler invocation; pass to `CacheBridge.executeQuery` |
| `streaming/HotReloadingModelRegistry.java` | In-memory overlay; `register(modelName, SemanticTable)` |
| `streaming/ModelRegistry.java` | **The** lookup seam (`SemanticTable get(modelName)`) |
| `streaming/YamlModelRegistry.java` | Loads YAML → `Map[String, SemanticTable]` via `YamlLoader.loadDir` |
| `streaming/StreamingService.java` | Resolve model + pass to `SparkStreamingQueryLauncher` |
| `streaming/SparkStreamingQueryLauncher.java` | `StreamingQuery start(SemanticTable, ...)` |
| `streaming/StreamingQueryLauncher.java` (interface) | Same |

**Zero `core.Model` usage** in the platform. The platform is 100% `SemanticTable`-coupled.

### The current workaround pattern

The platform has worked around the `SemanticTable.Dataset.rdd` journal-safety problem with a consistent pattern:

```java
// PATTERN: compile in HANDLER scope (NOT inside Restate.run)
final SemanticTable compiled = compileFromYaml(yaml, modelName, this.spark);
// Then ONLY the durable side effect goes in Restate.run:
final ModelDefinition persisted = Restate.run(
    "model.persist", ModelDefinition.class,
    () -> store.registerIfAbsent(modelName, nextVersion, yaml, hash, registeredAt, lineageJson));
```

**Per `ModelService.java` line 176-182:**
> *"STEP A: compile in handler scope. `SemanticTable` carries a `Dataset.rdd` chain that Jackson cannot round-trip through the Restate journal; the compile is a pure function and re-runs cheaply on journal replay. Keeping it OUT of `Restate.run` avoids the `InvalidDefinitionException` that `ModelServiceEndToEndTest`'s actual `@RestateTest` probe surfaced."*

**The platform works around the problem** by:
1. Resolving `SemanticTable` from the registry each handler invocation (handler scope, not journaled)
2. Compiling YAML → `SemanticTable` in handler scope (pure function, re-runs cheaply on replay)
3. Only the **durable side effect** (Postgres `INSERT`) goes in `Restate.run` — returns a small `ModelDefinition` record (Jackson-clean)
4. `RestateCachedRow` (custom Java record) replaces `Array[Row>` for query results (already done)

This works. The platform is functional. But it's complex and limits future use cases.

## 2. The migration target — `core.Model`

### Why `core.Model` is journal-friendly

`core.Model` is **engine-portable pure data**:

```scala
final class Model private[model] (
    val name:              String,
    val description:       Option[String],
    val source:            SourceRef,
    val dimensions:        List[Dimension],
    val measures:          List[Measure],
    val calculatedMeasures: List[CalculatedMeasure],
    val joins:             List[JoinSpec],
    val filters:           List[FilterSpec],
    val rollups:           List[RollupSpec],
    val defaultPolicies:   ModelPolicyDefaults,
    val extensions:        Map[String, ExtensionValue],
) extends Serializable
```

- **Zero Spark imports** (boundary contract)
- `extends Serializable` (Jackson-clean via ScalaModule)
- All fields are immutable `val`s
- Sealed-trait variants (`SourceRef`, `ModelStatus`) — Jackson handles them via discriminator (with `ScalaModule`)

### What the migration unlocks

Once `core.Model` is the canonical type, the platform can:

1. **Journal the model itself** if needed (e.g., for cross-handler model versioning state)
2. **Cache models across handler invocations** without the "resolve fresh each time" overhead
3. **Pass models as Restate state values** (`Restate.state().set("model", model)`)
4. **Eliminate the "compile in handler scope" workaround** — since the model is journal-safe, you can compile inside `Restate.run` if desired
5. **Use the portable reader** (from `semanticdf-portable-loader`, PR #439) directly in the platform (eliminating the dependency on `semanticdf-spark`'s legacy `YamlLoader`)

## 3. The migration — 4 sub-PRs

### Sub-PR #4.1: Audit (this PR — doc only, no code)

**Status:** in progress.

### Sub-PR #4.2: Migrate `ModelRegistry` (the seam)

**Scope:** ~300-500 LoC.

The `ModelRegistry` interface is the single seam where `SemanticTable` flows through. Migrating this seam unlocks every downstream use.

```java
// Before:
public interface ModelRegistry {
    SemanticTable get(String modelName);
}

// After:
public interface ModelRegistry {
    Model get(String modelName);  // core.Model
}
```

**Files touched:**
- `streaming/ModelRegistry.java` (interface signature change)
- `streaming/YamlModelRegistry.java` (use the portable reader instead of legacy `YamlLoader`)
- `streaming/HotReloadingModelRegistry.java` (overlay stores `core.Model`)
- Tests in `streaming/YamlModelRegistryTest.java`, `streaming/HotReloadingModelRegistryTest.java`

**Trade-off:** the `YamlModelRegistry` currently uses `YamlLoader.loadDir(path, spark)` (legacy, Spark-coupled). After migration, it should use `DualManifestReader.load(path, spark)` (from PR #441). The portable path bypasses `SemanticTable` entirely.

### Sub-PR #4.3: Migrate `ModelService.register` (the canonical write path)

**Scope:** ~500-800 LoC.

This is the **make-or-break** change. The current `register` handler:

```java
// STEP A: compile in handler scope. SemanticTable carries Dataset.rdd...
final SemanticTable compiled = compileFromYaml(yaml, modelName, this.spark);
```

After migration:

```java
// STEP A: compile in handler scope (or even in Restate.run — the model is journal-safe).
final Model compiled = compileFromYaml(yaml, modelName, this.spark);
// compiled is core.Model: pure data, journal-clean, no Dataset.rdd.
```

**Files touched:**
- `model/ModelService.java` (replace `SemanticTable` with `Model` in the `register` handler)
- `model/PostgresModelStore.java` (the persisted `manifest_yaml` may need to become a portable YAML or a serialized `Model` JSON; future work)
- `model/ModelServiceEndToEndTest.java`, `model/ModelServiceHotReloadTest.java`, `model/ModelServiceStructuralTest.java`

**Trade-off:** This is the **riskiest sub-PR** because it touches the canonical write path. The end-to-end tests (`@RestateTest`) are the safety net.

### Sub-PR #4.4: Migrate `QueryService` + `StreamingService` (the consumers)

**Scope:** ~500-800 LoC.

The consumers (query + streaming) don't journal models — they just resolve `SemanticTable` per handler invocation. The migration is straightforward: replace `SemanticTable` with `Model` in the local variable, and pass `Model` to the library's compile/execute functions (which already take `Model`).

**Files touched:**
- `query/QueryService.java`
- `query/RestateCachedRow.java` (no change — already a custom record)
- `streaming/StreamingService.java`
- `streaming/SparkStreamingQueryLauncher.java`
- `streaming/StreamingQueryLauncher.java` (interface)
- `query/QueryServiceCachePoisoningTest.java`, `query/QueryServiceEndToEndTest.java`, `query/QueryServiceRestateEndToEndTest.java`, `query/QueryServiceStampedeTest.java`, `query/QueryServiceStructuralTest.java`, etc.
- `streaming/StreamingServiceIntegrationTest.java`, `streaming/StreamingServiceTest.java`, `streaming/StartupReconcilerTest.java`, etc.

**Trade-off:** Lots of test updates. Each test that uses `SemanticTable` needs to migrate to `Model`.

### Sub-PR #4.5: Migrate platform tests (verification)

**Scope:** ~300-500 LoC (mostly mechanical).

Every test that constructs or asserts on `SemanticTable` needs to be migrated to `Model`. The library's `ModelBridge.toModel(SemanticTable)` is the bridge during transition (deprecated in 3B but kept for compatibility).

This is **largely mechanical** — pattern-replace `SemanticTable` with `Model`, adjust assertions.

## 4. Per-PR design constraints (9 skills applied)

For each sub-PR, the design must satisfy:

- **karpathy §1 (surface assumptions)**: every PR's doc states the design choice, surface tradeoffs, what's out of scope.
- **karpathy §2 (minimum code)**: don't refactor more than needed. Each PR migrates ONE concern.
- **karpathy §3 (surgical)**: only touch the files needed for the migration step. Don't refactor unrelated code.
- **scala-data-driven-refacer §1**: `core.Model` is pure data; the platform consumes it without adding behavior.
- **scala-data-driven-refacer §2**: validity is enforced at the boundary (portable reader does `Model.of` validation).
- **scala-jvm-safety**: temp file cleanup (already done in current code per #2); no new resources.
- **scala-error-handling §1**: existing typed errors propagate; new errors (e.g., `MalformedResponse`) are sealed ADT cases.
- **scala-impact-analysis §4**: each sub-PR is a SEPARATE branch with its own test surface.
- **scala-perf-testing**: no hot-path regressions; benchmark before/after.
- **scala-spark-batch-bugs**: closures captured in `Restate.run` no longer carry `Dataset.rdd` (they carry `Model`); closures are journal-safe.
- **scala-jar-packaging**: no new dependencies (the portable loader is already a sibling module).

## 5. Known limitations + risks

### Limitations inherited from `ModelBridge.toModel`

Per `ModelBridge.toModel`'s docstring:
1. Measure aggregate defaults to `Sum` (can't statically determine from closure)
2. Dimensions simplified to `FieldRef(name = expr)`
3. Filters not converted (Predicate type duplication)
4. `CalculatedMeasure`s not converted (CalcGraph is Spark-flavored)
5. Rollups not converted
6. `defaultPolicies` defaults to `none`
7. `extensions` defaults to empty

These limitations would propagate to the platform if we use `ModelBridge.toModel` as the bridge. **Mitigation:** use the **portable reader** (`semanticdf-portable-loader`) instead — it directly produces `Model` without these limitations, BUT it requires the YAML to be in the **portable format** (not the legacy format).

**For the platform migration**, we have two options:
- **A**: Migrate the platform's example YAMLs to the portable format (work for `semanticdf-portable-loader`). Bigger scope; needs YAML migration tooling.
- **B**: Use `ModelBridge.toModel` for now (accept limitations); add a follow-up to migrate YAMLs.

**My recommendation: B for sub-PRs 4.2-4.4, then a follow-up for A.** This keeps each sub-PR focused.

### Risks

1. **`ModelBridge.toModel` performance**: every model lookup calls `ModelBridge.toModel`. This was previously a one-time cost (at YAML load time). Now it's per-handler-invocation. **Mitigation:** cache the `Model` in the registry (which is what `HotReloadingModelRegistry` already does — just stores `Model` instead of `SemanticTable`).
2. **Test surface changes**: every test that touches `SemanticTable` needs updating. ~30 test files affected.
3. **Binary compatibility**: the `ModelRegistry` interface change is a breaking change for any external consumers. Per the v0.3.1 design (semantic versioning), this is fine for a minor release (no published JAR yet — platform is `0.1.0-SNAPSHOT`).

## 6. Open questions (need answers before sub-PR 4.2)

1. **`Model` field preservation**: does `Model` carry enough info for the platform's needs? Specifically, does the platform need anything from `SemanticTable` that's NOT in `Model` (e.g., `Dataset.rdd` access at runtime)?
2. **Manifest YAML round-trip**: should the platform persist the YAML OR the JSON-serialized `Model`? YAML preserves readability; JSON is canonical.
3. **Migration of example YAMLs**: should we migrate the example YAMLs in the same PR, or follow up?
4. **Versioning strategy**: how does the platform handle the migration of existing v0.1.0-SNAPSHOT platform instances? Migration script?

Per "minimum code", I'll defer answers to the relevant sub-PRs. Sub-PR #4.2 starts with assumption #1 (Model has enough info) and surfaces the actual problem.

## 9. Trigger conditions for revisiting this design

1. A real consumer of the platform requests journaled model state (cross-handler versioning).
2. The `ModelBridge.toModel` limitations start to bite (e.g., measure aggregate detection).
3. A new engine adapter (e.g., the upcoming Snowflake/BigQuery/Redshift adapters) needs `Model` instead of `SemanticTable`.
4. The `RestateCachedRow` pattern is generalized — maybe other types need custom Serde too.

When any of these fire, revisit this doc and start with the first unimplemented sub-PR.
