- **Data-oriented** (from the base skill + DE checklist: "data outlives layers", "follow the data across the boundary", "distinguish hot path from cold path")
- **Performance** (from the skill's operating rule: "On hot paths... treat indirection and allocation cost as a first-class review criterion, on par with the dependency rule itself")

**Method**: SocratiCode impact + symbol + graph queries; per-file hot/cold path classification; trait-mixin runtime cost analysis; cache/streaming path tracing.
**Date**: this session.

> **Mantra:**
> 1. **The dependency rule is the only rule.** Source code dependencies point inward, always. Everything else is a heuristic.
> 2. **Data outlives layers.** Model the data and its transformations first; hang the layers off that, not the other way around.
> 3. **Every boundary has a price.** An abstraction earns its place by isolating volatile decisions or hot-path data shape — not by convention.
> 4. **Follow the data across the boundary.** At every crossing, ask: what shape enters, what shape leaves, what got copied, what got allocated.
> 5. **Purity is not the deliverable. A working, changeable, fast-enough system is.**

## 2. Hot path identification (per the DE checklist)

The skill says: "Distinguish hot path... from cold path... indirection cost matters on the former, matters much less on the latter."

### Hot path A — `toDataFrame` (batch terminal)

Three paths through `toDataFrame`:

| Path | When | Cost | Inherent? |
|---|---|---|---|
| **A1: Fast path** (no audit, no cache) | always | `root.compile(spark)` | inherent |
| **A2: Cache hit** | cached query reused | `parallelize(rows.toSeq)` of already-materialized rows | inherent to caching |
| **A3: Cache miss** | cache enabled, no hit | `compile + collect + parallelize` (full materialization) | inherent to caching |

**All three paths have inherent cost.** The `collect + parallelize` round-trip on the cache miss is the cost of materializing once and replaying — there's no way to avoid it without breaking cache semantics.

### Hot path B — `compile(spark)` (op tree → DataFrame)

`SemanticOpVisitor.visit(op)` (in `SemanticOpTraversal.scala`) uses **pattern match dispatch** on the 10-case sealed ADT. The Scala compiler compiles this to a **jump table**, not a virtual call.

Per `SemanticOp.compile` for the leaf cases: `SemanticTableOp.compile` returns `table` directly (no copy); `SemanticStreamingTableOp.compile` returns `stream` directly (no copy). **No wasteful copies on the hot path.**

### Hot path C — `toStreamingQuery` foreachBatch (per microbatch)

For each microbatch:
- **If `withAuditSink` is set**: 1 job for `batchDf.count()` per batch (per the v0.2.0 cost note from PR #191). Documented in `SemanticTableStreaming.scala` and `docs/design/audit-log.md`.
- **The result cache is disabled inside foreachBatch** (`resultCache = None`). Per the codebase comment: "the cache key does not include batch identity, so the first micro-batch's result could be returned for every subsequent batch. Disabling the cache here means each batch is computed fresh." ✅
- **The op tree is re-walked per batch** (filter-only path) or re-aggregated per batch (windowed path). Inherent to streaming — each batch is new data.

### Hot path D — `collectAs[T]` / `queryAs[T]` (typed-result terminal)

- `collectAs[T]`: `toDataFrame(spark).collect().toSeq.map(decoder.decode)` — collect + decode per row.
- `queryAs[T]`: `query(...).execute(spark).as[T](encoder)` — uses Spark's native `Encoder[T]`.

The `ResultDecoder.decode(row)` is invoked **once per result row** when collecting, not during streaming. This is the **only data-shape boundary** in the typed surface — and it's a one-time per-result-set cost, not per-row during streaming.

## 3. Trait mixin runtime cost (performance-oriented question)

The v0.2.0 split moved 80 methods from `SemanticTable.scala` into 4 traits (`SemanticTableCore`, `Streaming`, `Mutation`, `Collection`). The runtime cost question: **does trait mixin add overhead?**

Verified:

| Concern | Verified |
|---|---|
| Methods in traits — do they have implementations (not abstract)? | ✅ All 4 traits' public methods are concrete (have `=` bodies) |
| Does trait body access `self.field` or `this.field`? | ✅ All trait bodies use `this.field` directly (no `self.` indirection); `self: SemanticTable =>` is only an annotation |
| Are the 4 trait classes compiled with default methods on the class? | ✅ Yes — Scala compiles trait mixin to direct method calls on the class |
| Is there any virtual dispatch at the call site? | ✅ No — traits are mixed in linearly; `instance.method()` is a direct call |

**Conclusion**: trait mixin has **zero runtime overhead**. The Scala compiler emits the same bytecode as if the methods were declared directly on the class.

**Performance verdict**: ✅ The trait split earns its keep on organizational grounds with **zero performance cost**.

## 5. Data-shape + performance findings

### Critical

**None.** No hot-path violation. No avoidable allocation/copy. No hidden data shape transformation.

### High

**Finding H1 — Streaming audit emit is a documented cost (from v0.2.0 PR #191, carrying forward).**

- **Location**: `SemanticTableStreaming.scala` `emitStreamingAudit` (line 457)
- **Cost**: 1 Spark job per microbatch when `withAuditSink(sink)` is set, because `batchDf.count()` is needed to populate the audit event's `rowCount` field.
- **Why**: The PR #190 fix added the per-batch `rowCount` so the audit log is correct. The cost is inherent to emitting a rowCount per batch — without the count, the field would be `0` and the audit log would be a silent wrong answer.
- **Mitigation**: documented in `docs/design/audit-log.md` and the `withAuditSink` cost note in `SemanticTableStreaming.scala`. Users who care about per-microbatch latency can opt out by not setting `withAuditSink` on streaming models.
- **Status**: documented (L1 from PR #191). **Not a regression from v0.2.0** — the trait split did NOT introduce this cost. It's been there since v0.1.17 (PR #190).

### Medium

**Finding M1 — Cache miss path requires `collect + parallelize` (full materialization).**

- **Location**: `SemanticTableCore.scala` cache miss path (~line 145)
- **Cost**: for large result sets, this materializes the result to the driver and replays from driver. The driver memory footprint = full result set.
- **Why inherent**: the cache stores materialized rows; you can't replay without materializing.
- **Mitigation**: use a bounded cache (`ResultCache.inMemory(256)`) and accept the trade-off.
- **Status**: documented in `docs/design/result-cache.md`. **Not a regression from v0.2.0.**

### Low

**Finding L1 — `compileWindowedAggregation` re-aggregates per microbatch (Spark Structured Streaming state management).**

- **Location**: `SemanticTableStreaming.scala` ~line 437
- **Cost**: each microbatch triggers a stateful aggregation against the watermarked source. This is inherent to Spark Structured Streaming's design — Spark maintains the state, we just invoke `groupBy/agg` per batch.
- **Why inherent**: this is how Spark Structured Streaming works. We're the *terminal*, not the aggregation engine.
- **Mitigation**: use `outputMode = "append"` (default) or configure Spark's state store for larger windows.
- **Status**: inherent to the streaming model. Not a v0.2.0 regression.

**Finding L2 — `substituteStreamingLeaf` re-walks the op tree per microbatch.**

- **Location**: `SemanticTableStreaming.scala` ~line 381
- **Cost**: per microbatch, the filter-only path walks the op tree once and constructs a new op tree via `.copy(source = ...)`. The walk is O(tree size); the new tree is the same size.
- **Why inherent**: the `foreachBatch` API gives us a `DataFrame` batch; we have to substitute it into the op tree to apply the user's filters/transforms per batch.
- **Mitigation**: if you don't need the filters re-applied per batch, build the model without them (use `toSemanticTable` once and wire the same `Streaming DataFrame` directly to your sink).
- **Status**: inherent to the streaming architecture. Not a v0.2.0 regression.

## 7. What I am NOT recommending changing

- **Trait mixin is fine** — zero runtime overhead. Don't undo the split for performance reasons.
- **The streaming audit cost is documented and opt-in** — don't remove the `count()` call. Without it, the audit log would silently report `rowCount=0` for every batch, which PR #190 explicitly fixed.
- **The result cache miss cost is inherent to caching** — don't add a "streaming-only cache" mode; the streaming path already disables cache correctly.
- **The op-tree `.copy(source = ...)` per microbatch is inherent to the foreachBatch API** — Spark hands us a DataFrame per batch, we have to substitute it into the op tree.
