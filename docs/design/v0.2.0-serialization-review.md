# Clean-Architecture Review — PR #201 (Cluster-Mode Serialization) Post-Merge

**Scope**: validate v0.2.0 cluster-mode readiness after PR #201 (commit `4604448`). Stacked lenses: **DE** (Spark batch + streaming), **JVM-Scala** (Scala 2.13). Streaming vocabulary applied only to the `foreachBatch` audit path.
**Date**: this session.
**Main is at**: `4604448 fix(serialization): make SemanticTable Java-serializable for cluster mode (+ doc fixes) (#201)`.

> **Mantra:**
> 1. **The dependency rule is the only rule.** Source code dependencies point inward, always. Everything else is a heuristic.
> 2. **Data outlives layers.** Model the data and its transformations first; hang the layers off that, not the other way around.
> 3. **Every boundary has a price.** An abstraction earns its place by isolating volatile decisions or hot-path data shape — not by convention.
> 4. **Follow the data across the boundary.** At every crossing, ask: what shape enters, what shape leaves, what got copied, what got allocated.
> 5. **Purity is not the deliverable. A working, changeable, fast-enough system is.**

## 1. Hot path classification

The PR adds no new hot-path operations. It modifies three existing types for cluster-mode serialization only. Per-file classification of the changed files:

| File | Path | Cost | Inherent? | Regression vs v0.1.17? |
|---|---|---|---|---|
| `SemanticTable.scala` | `extends Serializable` | one marker interface on the class; no field added; constructor unchanged | no (just a marker) | **none** |
| `SemanticTable` field access (hot) | `this.auditSink`, `this.resultCache` etc. | `invokevirtual` on accessor — identical bytecode to pre-#201 | no | **none** |
| `InMemoryAuditSink.emit` (hot when audit enabled) | `buf.addLast` + `buf.removeFirst` on `java.util.ArrayDeque` | `O(1)` amortized; same as `mutable.Queue`'s amortized bound | yes | **positive**: `ArrayDeque` allocates less per op than Scala's `mutable.Queue` (no wrapper allocation, no Scala collection state) |
| `InMemoryResultCache.get` / `put` (hot when cache enabled) | `java.util.LinkedHashMap` accessOrder + `java.util.HashMap`/`HashSet` sidecar | `O(1)` lookup, `O(1)` LRU reorder; identical asymptotic cost to `mutable.HashMap` | yes | **neutral**: identical backing data structure |
| `SemanticTable.toDataFrame` (hot) | unchanged | unchanged | n/a | **none** |
| Streaming `emitStreamingAudit` (hot per microbatch) | `batchDf.count()` per microbatch when `withAuditSink` is set | 1 Spark action per batch | yes (documented PR #191, reaffirmed PR #201) | **none** |

**Verdict**: PR #201 is **performance-neutral or slightly positive**. The Scala-collection → `java.util` swap is mechanically a downgrade in Scala idiomaticity but an upgrade in raw allocation/perf characteristics for the audit sink (avoiding `mutable.Queue`'s wrapper objects). The cache swap is byte-for-byte equivalent.

## 4. Data-shape change map

PR #201 changes two data shapes; both reduce shape complexity:

| Change | From | To | Cost per change |

## 6. Severity-ranked recommendations

### High

#### Finding #1 — `OssieReader.parse` leaks a `BufferedReader` file handle per call

**Where**: `src/main/scala/io/semanticdf/adapters/OssieReader.scala` line 99.

```scala
val root = new Yaml().load[java.util.Map[String, Any]](
  Files.newBufferedReader(source))
```

`Files.newBufferedReader(source)` returns a `BufferedReader`. SnakeYAML's `Yaml.load(Reader)` does **not** close the passed Reader (this is documented SnakeYAML behavior — it only consumes from it). The reader is dropped on the floor after the parse completes (or if it throws partway). Every call to `OssieReader.parse` opens a file descriptor that is only released when the GC reclaims the `BufferedReader` (likely after the JVM-level `MBean` `OperatingSystemMXBean` cleans up via `FileDescriptor` finalization).

The leak is **masked by a wrong comment in the test**:

```
// In OssieReaderLeakSpec.scala:
//   "File handle leaks: SnakeYAML's `Files.newBufferedReader` is used
//    inside a try-finally by SnakeYAML itself; the reader doesn't hold
//    file handles beyond the parse call."
```

This claim is **factually incorrect**. SnakeYAML does not close the passed `Reader`. The test never asserts anything about file handle counts (only heap delta, which doesn't catch FD leaks). On a long-lived driver calling `OssieReader.parse` repeatedly (e.g., a server hot-reloading Ossie definitions), FDs accumulate until the OS limit (`ulimit -n`, default 1024 on Linux).

**Why PR #201 didn't fix it**: PR #201's scope was specifically `SemanticTable` + `AuditSink` + `ResultCache`. The Ossie reader sits in the adapters package and was not touched. The pre-existing leak survived the v0.2.0 review (the data-oriented review checked the same `Files.newBufferedReader` but did not flag the missing close).

**Concrete fix** (one line):

```scala
// Replace:
val root = new Yaml().load[java.util.Map[String, Any]](
  Files.newBufferedReader(source))

// With:
val root = {
  val reader = Files.newBufferedReader(source)
  try new Yaml().load[java.util.Map[String, Any]](reader)
  finally reader.close()
}
```

**Test to add** to `OssieReaderLeakSpec.scala`:

```scala
test("OssieReader: parse does not leak file handles") {
  // Snapshot /proc/self/fd count, parse 1000 times, assert delta is 0.
  val before = java.nio.file.Files.list(java.nio.file.Paths.get("/proc/self/fd")).count()
  val path = Paths.get("src/test/resources/ossie-fixtures/medium-ossie.yaml")
  for (_ <- 0 until 1000) {
    val _ = OssieReader.parse(path)
  }
  val after = java.nio.file.Files.list(java.nio.file.Paths.get("/proc/self/fd")).count()
  assert(after <= before + 1, s"FD count grew: before=$before after=$after")
}
```

Plus fix the wrong comment in `OssieReaderLeakSpec`'s preamble — it claims SnakeYAML closes the reader, which is false.

### Medium

#### Finding #2 — `SerializationSpec` does not exercise the new fields (`auditSink`, `auditRequest`, `resultCache`, `sourceTable`) with non-`None` values

**Where**: `src/test/scala/io/semanticdf/SerializationSpec.scala`, lines 152–186.

The two `SemanticTable` round-trip tests construct the model with default setters and never set `auditSink`, `auditRequest`, `resultCache`, or `sourceTable`:

```scala
val model = io.semanticdf.toSemanticTable(flightsDf, name = Some("flights"))
  .withDimensions(Dimension("carrier", t => t("carrier")))
  .withMeasures(Measure("pax_sum", t => sum(t("pax"))))
val round = roundTrip(model)
```

The four `Option`-typed fields all default to `None`, so the test only exercises the op-tree + name + dimensions + measures + version + status branches of the constructor. **It does not verify** that `Some(InMemoryAuditSink())` or `Some(InMemoryResultCache())` round-trips — which is the entire point of PR #201.

The change is mechanically straightforward (`extends Serializable` is a marker), so the gap is unlikely to hide a bug — but the test naming ("the full op tree round-trips") is misleading, and a future regression that makes `AuditSink` non-Serializable (e.g., adding a non-Serializable field) would not be caught.

**Concrete fix** (add one test, ~20 lines):

```scala
test("SemanticTable: round-trip preserves auditSink + resultCache (PR #201 fix)") {
  import org.apache.spark.sql.functions.sum
  val cache = io.semanticdf.cache.ResultCache.inMemory(maxEntries = 4)
  val sink  = io.semanticdf.audit.AuditSink.inMemory(maxEvents = 4)
  val model = io.semanticdf.toSemanticTable(flightsDf, name = Some("flights"))
    .withDimensions(Dimension("carrier", t => t("carrier")))
    .withMeasures(Measure("pax_sum", t => sum(t("pax"))))
    .withAuditSink(sink)
    .withResultCache(cache)
  val round = roundTrip(model)
  assert(round.auditSink.isDefined, "auditSink must survive round-trip")
  assert(round.resultCache.isDefined, "resultCache must survive round-trip")
  // Functional smoke test: the round-tripped sink and cache are still usable.
  round.auditSink.get.emit(io.semanticdf.audit.AuditEvent(
    ts = java.time.Instant.now(), model = "test", version = 0,
    measures = Nil, dimensions = Nil,
    whereHash = None, havingHash = None,
    rowCount = 1, elapsedMs = 1, status = "ok"))
  assert(round.auditSink.get.snapshot().length == 1)
}
```

#### Finding #3 — `PredicateAst.Predicate.cache` is a `scala.collection.mutable.Map` and breaks post-compile cluster-mode serialization for non-equi joins

**Where**: `src/main/scala/io/semanticdf/PredicateAst.scala`, line 99.

```scala
@volatile private var cache: scala.collection.mutable.Map[(Any, Any), Column] = null
```

This is a **lazy memoization cache** — `null` initially, populated on first call to `toColumn(leftSide, rightSide)`. When populated, it holds `scala.collection.mutable.Map`, which is not Java-Serializable.

PR #201 did not address this because `PredicateAst` was not in scope. But it has the same cluster-mode implication that PR #201 set out to fix: a `SemanticTable` containing a non-equi join's `PredicateAst.Predicate`, after `compile()` has been called on the driver (which calls `toColumn` and populates the cache), cannot be re-serialized for executor distribution. The `@volatile private var` survives Java's default case-class serialization (the case class's auto-generated `writeObject` writes the field verbatim — null is fine, but a populated `mutable.Map` will either fail outright or write an unreadable form).

**Why this is Medium, not High**: the realistic cluster-mode flow is:
1. Build `SemanticTable` on driver (cache = null)
2. Capture in a UDF / broadcast / accumulator → serialize to executors

Step 1 does not populate the cache (the cache is populated only by `toColumn`, which is called during `compile()` on `toDataFrame`). The user would have to:
1. Build `SemanticTable`
2. Call `toDataFrame` once on the driver (cache populated)
3. THEN serialize for distribution

That triple-step is unusual. Most UDFs/broadcasts capture a freshly-built `SemanticTable` and go straight to serialization. So the realistic risk is low. But the door is open, and the field could surprise a future cluster-mode user.

**Concrete fix** (smallest, lowest-risk):

```scala
// Add to PredicateAst.Predicate's case-class fields, OR mark the cache transient:
@scala.beans.Transient  // OR @transient (Java)
@volatile private var cache: scala.collection.mutable.Map[(Any, Any), Column] = null
```

`@transient` will cause Java's default case-class serialization to skip the field — the deserialized AST starts with `cache = null`, exactly the same as a freshly-built one. The lazy repopulation cost is paid on the executor once, identical to the driver-side cost.

### Low

#### Finding #4 — `Dimension.expr` (the lambda) is asserted as round-trippable but never called after deserialization

`SerializationSpec.Dimension: Java-serializable` checks `name`, `description`, `metadata`, `isEntity`, `exprString` after `roundTrip(dim)` — but never calls `round.expr(t)` to confirm the lambda still produces a `Column`. The class comment correctly notes that "the lambda's source isn't recoverable from the bytecode" (true for `toString` / source-level introspection), but the test should at least exercise the deserialized lambda once to prove the anonymous-inner-class round-trip is sound:

```scala
test("Dimension: deserialized expr still produces a Column (lambda survives)") {
  val dim = new Dimension("carrier", (t: SemanticScope) => t("carrier"))
  val round = roundTrip(dim)
  // smoke-test: round.expr builds a Column against the fixture DataFrame
  val col = round.expr(io.semanticdf.BaseScope(flightsDf))
  assert(col != null)
  assert(col.expr == t.expr(io.semanticdf.BaseScope(flightsDf)).expr)
}
```

Cost: 6 lines. Value: closes the "did the lambda actually survive" question for the case where the lambda captures no external state (the typical case).

#### Finding #5 — `AuditEvent` has no `@SerialVersionUID`

`AuditEvent` is a `final case class` with a `version: Int = 0` field. Adding a new optional field would shift the case-class-generated `serialVersionUID` (computed from class structure), breaking cluster-mode compatibility for any cached `AuditEvent` already on an executor. The library has a `version: Int` semantic-version field on the data, but no Java serialization `serialVersionUID`.

**Concrete fix** (one line):

```scala
@SerialVersionUID(1L)
final case class AuditEvent(...)
```

Add it to `QueryRequest` too. Same defensive rationale.

#### Finding #6 — `extends Serializable` is a marker; a doc note would help

The `extends Serializable` on `SemanticTable` is followed by 4 traits. The trait mixin doesn't extend `Serializable` themselves — they inherit the marker's effect only via the `SemanticTable` host class. If a future refactor moves a field from `SemanticTable` into one of the traits, that field would silently lose `Serializable`. A one-line comment on each trait ("trait is mixed into a Serializable host") would future-proof against this. Optional, very low value, but it's the kind of inline doc that pays off 18 months from now when nobody remembers PR #201.

## 7. What you are NOT recommending changing

- **`extends Serializable` cost**: zero hot-path cost. Confirmed by:
  - `Serializable` is a marker interface — no fields, no methods
  - Class loading: the JVM does not load extra metadata for `Serializable`
  - Field access: `invokevirtual` on accessors is identical for Serializable and non-Serializable classes
  - Reflection: only matters when `writeObject`/`readObject` is invoked (which is the actual purpose of the marker)
  - Trait mixin: the cross-trait `invokeinterface` is amortized to zero by the JIT after type profiling, exactly as documented in `docs/design/v0.2.0-data-oriented-and-performance-review.md` §3

- **`mutable.Queue` → `ArrayDeque`**: this is a strict improvement on the audit hot path. `ArrayDeque` allocates no per-op wrapper, while Scala's `mutable.Queue` allocates a node per `enqueue`. The `ArrayDeque.addLast` + `removeFirst` pattern is the canonical JDK idiom for a bounded FIFO.

- **`mutable.HashMap`/`mutable.Set` → `java.util.HashMap`/`HashSet`**: same backing data structure, no behavioral change.

- **`SemanticTable` constructor signature**: unchanged. 8 fields, all positional/named, all initialized via `new SemanticTable(...)` from the trait setters. PR #201 added no fields, no setters, no validation logic.

- **Streaming audit cost (`batchDf.count()` per microbatch)**: documented in `SemanticTableStreaming.scala` line 191 (PR #191) and line 463 (the actual call). PR #201 does not change this. The cost is inherent to the feature ("the audit log's per-batch `rowCount`" is the whole point) — dropping it would reintroduce the bug PR #190 fixed (silent `rowCount=0` for streaming).

- **`SemanticTableSerializationSpec` test existence**: 9 tests are present and pass. The PR achieves what it claims; the gap is in *coverage breadth* (not all fields tested), not in *correctness of what is tested*.

- **The `SemanticTableCore.toDataFrame` fast-path guard** (`if (auditSink.isEmpty && resultCache.isEmpty)`): unchanged. Same `invokestatic`-able `Option.isEmpty` check, same branch layout, no performance regression from PR #201.

- **Trait split cost**: zero. Same conclusion as `v0.2.0-data-oriented-and-performance-review.md` §3. PR #201 didn't touch the traits.

- **Schema contract map**: all 11 boundaries were either already explicit or made explicit by this PR. No new implicit boundaries were introduced.

- **`OkfGen.loadFile` / `SDFAdapter.parse`**: both use `Files.readString` (or `Files.readString`-equivalent) which opens and closes internally — no file-handle risk. These are not `Files.newBufferedReader` call sites, despite the user's prompt mentioning an `OkfCache.build` (which does not exist; the closest match is `OkfGen.generate` → `loadFile`, which is safe).

- **Spark session lifecycle in tools + examples**: every `getOrCreate()` is paired with a `finally spark.stop()` or runs at JVM exit. No leak.

- **Thread safety**: no `new Thread`, no `Executors`, no threadpools in production code. The 8-thread test in `leak/LeakSpec.scala:174` is a test fixture, not production.
