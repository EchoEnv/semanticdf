# Clean-Architecture Re-Review — v0.2.0 (with JVM-Scala lens applied)

**Scope**: re-review the `io.semanticdf/` package layout using the **stacked DE + streaming + JVM-Scala** reference set (per the skill: "A Scala Spark job reads both its domain reference and `jvm-scala.md` together").
**Method**: SocratiCode impact + symbol + graph queries; manual ring classification of every file; typeclass seam inventory; implicit-scope leak audit.
**Date**: this session.

> **Mantra:**
> 1. **The dependency rule is the only rule.** Source code dependencies point inward, always. Everything else is a heuristic.
> 2. **Data outlives layers.** Model the data and its transformations first; hang the layers off that, not the other way around.
> 3. **Every boundary has a price.** An abstraction earns its place by isolating volatile decisions or hot-path data shape — not by convention.
> 4. **Follow the data across the boundary.** At every crossing, ask: what shape enters, what shape leaves, what got copied, what got allocated.
> 5. **Purity is not the deliverable. A working, changeable, fast-enough system is.**

## 8. Findings by severity

### Critical

**None.** No dependency-rule violations, no data-loss risk, no implicit-scope leaks.

### High

**Finding H1 — Two typeclass seams are misplaced (jvm-scala.md "misplaced" category).**
- **`ResultDecoder[T]`** (at `src/main/scala/io/semanticdf/ResultDecoder.scala`) sits at the top level next to 29 unrelated files. It's a typeclass with a companion object holding instances + macros. Per jvm-scala.md, "the abstraction exists but the implementation/instance lives in a different module" is misplaced.
- **`SemanticField[T]`** (at `src/main/scala/io/semanticdf/SemanticField.scala`) sits at the top level. It's the typeclass seam for typed dimension/measure refs. Same misplacement.
- **Cost**: a reader hunting for "where do typed result refs live?" has to know that `SemanticField` is at the top level (no naming convention hint). IDE search helps but a directory would be faster.
- **Benefit of moving**: discoverability, matches the pattern of `adapters/`/`audit/`/`cache/` (which are exactly the same pattern: a typeclass + implementations + helpers).
- **Risk of moving**: low. The typeclass is referenced via implicit resolution at use sites, not by name from many files. Moving to `core/` or `typed/` would require updating the few files that import it.

### Medium

**None.** No over-engineered boundaries, no under-engineered boundaries worth flagging.

### Low

**Finding L1 — `SemanticManifest` case classes could share a sub-package with `YamlLoader` and `DbtManifestReader`.** These three files form a cohesive "manifest format" cluster. Per jvm-scala.md's "case classes used as entities should not carry framework-specific typeclass instances" rule, this would be safe to organize. But the **seam is already in `adapters/`** (the typeclass), so this is purely aesthetic — same value as the original sub-packaging claim but with the JVM-Scala lens applied.

**Finding L2 — `StreamingSupport` could share a sub-package with `TimeGrain`.** Both are streaming-specific. `StreamingConfig` is defined in `StreamingSupport.scala`. Cohesive. But adding a sub-package for one trait+helper doesn't add a seam — it's just visual organization.

**Finding L3 — `Predicate` + `PredicateAst` + `PredicateOps` + `PredicateAstWalker` could share a sub-package.** Four files, cohesive (predicate DSL + wire format + extension methods + visitor). But the seam here (`Predicate.Hasher` → `audit/PredicateHasher`) is already separated; the predicate files themselves don't introduce a new seam.

## 9. The corrected recommendation

My **earlier** recommendation was: "don't do any sub-packaging."

With the **JVM-Scala lens** applied, my **corrected** recommendation is:

**Do a small, targeted sub-packaging PR — but only for the 2 misplaced typeclass seams (Finding H1).** Here's why:

### What the skill ACTUALLY rewards

The skill's "earning its keep" pattern for typeclass-based seams is: **typeclass + instances + helpers in one named package**. We have 3 instances of this already (`adapters/`, `audit/`, `cache/`) and 2 instances where the pattern is broken (the typeclass is at the top level surrounded by other concerns).

The cleanest fix is to **create one new sub-package: `typed/`**, which would hold:
- `SemanticField.scala` (the typeclass + sealed `FieldKind` + value class `FieldRef` + `SemanticDimension` + `SemanticMeasure` instances + `FieldRef` companion)
- `CalcExpr.scala` + `CalcHelpers.scala` (the calc expression DSL)
- `TypedArithmetic.scala` + `TypedMeasure.scala` (the typed column / typed measure machinery)
- `ResultDecoder.scala` + `ResultDecoderMacros.scala` (the typed-row-result typeclass + derive macro)

That's **7 files, ~510 lines** moved into `typed/` — a **single cohesive concern**: "the typed/compile-time-checked surface of the semantic layer".

The volatile decision isolated by `typed/`: **"how typed references and typed results flow through the library."** This decision changes independently of (a) the manifest format (`adapters/`), (b) the audit log (`audit/`), (c) the cache (`cache/`), and (d) the op tree (`io.semanticdf` root).

### What I'd NOT do

- **Don't move `SemanticManifest` + `YamlLoader` + `DbtManifestReader` into `manifest/`.** The seam is already in `adapters/`. Moving these 3 files would be visual organization without an isolation benefit.
- **Don't move `Predicate` + family to `predicate/`.** Same reasoning — these are entities, not typeclass-based seams.
- **Don't move `StreamingSupport` + `TimeGrain` to `streaming/`.** Same reasoning.
- **Don't move `SemanticOp` + `SemanticOpTraversal` + `SparkFilterValidator` to `op/`.** Same reasoning.

### The skill's verdict on this

> "An abstraction earns its place by isolating volatile decisions or hot-path data shape — not by convention."

`typed/` isolates the "typed-references-and-results" volatile decision. That's a real boundary, not convention. ✅
